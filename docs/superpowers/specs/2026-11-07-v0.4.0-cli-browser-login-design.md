# Anchor 0.4.0: CLI login through the browser

Status: proposed (2026-11-07). Ships in release **0.4.0**, together with typed values
(`2026-11-07-v0.4.0-typed-values-design.md`).

## Intent

`anchor login` today asks for an email and password in the terminal and sends them to the server.
Developers would rather log in the way `gh auth login` works: the CLI shows a short code, the
browser opens the Anchor dashboard, and they approve with the web session they already have. The
password never touches the terminal, and once the dashboard gains SSO, the CLI gets it for free.

## Decisions (with the user)

- **Flow:** device authorization (modeled on RFC 8628) and approved in Anchor's own dashboard. No
  external identity provider, and no localhost redirect, so it works over SSH and in containers.
- **Release:** part of 0.4.0.
- **Password login stays**, but is no longer the default. It is reached with `--with-password`;
  `--email` and `--password-stdin` imply it, so existing scripts keep working unchanged.

## Goals

- `anchor login` (no flags) runs the browser flow and stores a normal `cli` session, as today.
- Works without a local browser: the URL and code are printed, and any device can approve.
- Only a person signed in to the dashboard with a **web** session can approve. A CLI session or a
  service token cannot approve, so a stolen CLI token cannot mint more sessions.
- Every approval, denial and resulting login is audited.

## Non-goals

- SSO (GitHub/Google/OIDC) for the dashboard: a later release.
- Approving from the CLI or the API with a bearer token.
- Scoped or shorter-lived CLI sessions (the existing 30-day `cli` session is reused).

## Flow

```
CLI                                 Server                         Browser (signed in)
POST /auth/cli/start  ───────────▶  create request (10 min)
◀── deviceCode, userCode, URL, interval
print "Code: WDJB-MJHT", open URL ─────────────────────────────▶  /cli/login?code=WDJB-MJHT
poll POST /auth/cli/token (every 5 s)                              GET  /auth/cli/requests/:code
◀── 202 pending                                                    shows code, client, IP, time
                                    status = approved  ◀────────── POST /auth/cli/requests/:code/approve
poll ───────────────────────────▶  create cli session, status = consumed
◀── 200 { user, token, expiresAt }
```

## Server

### Storage: migration `0006_cli_logins.sql`

Table `cli_logins`:

| Column | Notes |
|---|---|
| `id TEXT PRIMARY KEY` | `sha256Hex(deviceCode)`. The device code itself is never stored |
| `user_code TEXT NOT NULL UNIQUE` | `XXXX-XXXX` from the alphabet `BCDFGHJKLMNPQRSTVWXZ` (about 34.6 bits) |
| `status TEXT NOT NULL` | CHECK in `pending`, `approved`, `denied`, `consumed` |
| `user_id TEXT NULL` | references `users(id)` ON DELETE CASCADE; set on approval |
| `client_name TEXT NULL` | sent by the CLI (`<user>@<hostname>`), at most 100 chars; shown as untrusted text |
| `user_agent TEXT NULL`, `ip TEXT NULL` | of the `start` request (`cf-connecting-ip`) |
| `created_at`, `expires_at`, `last_polled_at INTEGER` | `expires_at = created_at + 600000` |

- `deviceCode` = `newToken("anc_dc")`, a new `TokenKind`: 32 random bytes, base64url, prefixed.
- At most **50 pending, unexpired** rows at once (instance-wide). Past that, `start` returns
  `429 rate_limited` "Too many pending CLI logins, try again later". This caps what anonymous
  traffic can write.
- The daily cron deletes rows whose `expires_at` is more than 1 day in the past.

### Endpoints (under `/api/v1`)

| Method and path | Auth | Result |
|---|---|---|
| `POST /auth/cli/start` body `{ clientName?: string }` | none | `200 { deviceCode, userCode, verificationUri, verificationUriComplete, expiresAt, interval: 5 }` |
| `POST /auth/cli/token` body `{ deviceCode: string }` | none | `202 { status: "pending" }`; `200 LoginResponse` with `token`; `429 rate_limited` when polled sooner than `interval`; `403 forbidden` "This login was denied"; `404 not_found` "This login request expired or does not exist" for unknown, expired or already-consumed codes |
| `GET /auth/cli/requests/:userCode` | **web session (cookie)** | `200 CliLoginRequestDto` while pending and unexpired, otherwise `404` |
| `POST /auth/cli/requests/:userCode/approve` | **web session (cookie)** + existing Origin check | `204`; `404` if it is not pending |
| `POST /auth/cli/requests/:userCode/deny` | **web session (cookie)** + existing Origin check | `204`; `404` if it is not pending |

- `verificationUri` = `<request origin>/cli/login`; `verificationUriComplete` adds `?code=<userCode>`.
- User codes in paths are matched case-insensitively, with or without the dash.
- The token exchange is single-use: one `UPDATE ... SET status='consumed' WHERE id=? AND
  status='approved'` decides the winner, and only the winner creates the session. The session
  uses `createSession(db, userId, "cli", <start user agent>, now)`. A user disabled between
  approval and exchange gets `403` "Account disabled", like password login.
- `CliLoginRequestDto = { userCode: string; clientName: string | null; userAgent: string | null; ip: string | null; createdAt: number; expiresAt: number }`.

### Audit

New actions, appended after the existing list (never renamed): `auth.cli_login_approved`,
`auth.cli_login_denied`. A successful exchange records `auth.login` with metadata
`{ client: "cli", method: "browser" }`; password login gains `method: "password"`. `start` and
polling are not audited (anonymous, high volume). The rate-limiting rule already documented for
`POST /api/v1/auth/*` covers both.

### Threats

- **Phishing with a code link.** An attacker starts a login and gets a victim to approve it. The
  approval page shows the code in large type, the client name, the IP and the age of the request,
  and the copy "Only approve if you just ran `anchor login` and this code matches your terminal".
  Requests expire after 10 minutes. This is the same accepted residual risk as `gh auth login`.
- **Guessing codes.** A user code alone grants nothing: approving it needs a signed-in web
  session, and the device code (256 bits) is the only thing that collects the token.
- **CSRF.** Approve and deny are cookie-authenticated POSTs, so the existing `checkOrigin`
  middleware applies; a test pins it.

## CLI

- `anchor login [--api-url <url>] [--no-browser]` runs the browser flow.
- `anchor login --with-password [--email <e>] [--password-stdin]` runs today's flow;
  `--email` or `--password-stdin` alone also select it.
- The same API URL safety check as today applies before any request. The prompt wording becomes
  `Log in to <url>?`, and in password mode it stays `Send your password to <url>?`.
- Output on stderr:
  `Open <verificationUriComplete> and confirm the code <USER-CODE>`, then
  `Waiting for approval…`.
- The browser is opened only when stdin and stderr are TTYs and `--no-browser` is not set, with
  `open` (macOS), `xdg-open` (Linux) or `cmd /c start ""` (Windows), passing the URL as an
  argument (never through a shell). A failure to open only prints the URL.
- Polling: every `interval` seconds; after a 429, add 5 seconds to the interval. It stops on 200
  (store the credential exactly as password login does), 403 (`CliError(EXIT.AUTH, "Login was denied in the browser")`),
  404 (`CliError(EXIT.AUTH, "Login request expired; run anchor login again")`), or Ctrl-C.
- Works without a TTY (it prints and polls); CI should keep using `ANCHOR_TOKEN`.

## Dashboard

- Route `/cli/login?code=XXXX-XXXX` uses `AuthLayout`. Signed-out users go through
  `/login?redirect=...` and come back (the existing `requireUser`).
- The page shows the code, the client name, the IP, "requested N minutes ago", the warning copy,
  and **Approve** / **Deny** buttons. Afterwards it shows "You can close this tab and return to
  your terminal." An unknown or expired code shows "This login request expired or was already
  used." With no `code` parameter, the page has a code input (for the printed-URL case).

## Approaches considered

1. **Device flow approved in the dashboard (chosen).** Works over SSH, no IdP configuration, and
   reuses web sessions.
2. **Localhost redirect with PKCE.** One fewer step, but breaks over SSH and in containers.
3. **External SSO.** Big per-deployment setup. Deferred; it would sit behind this same dashboard
   approval.

## Release

Included in the 0.4.0 changelog. Migration `0006_cli_logins` is applied by `pnpm deploy` and
Workers Builds. CLI 0.3.x keeps logging in with a password; CLI 0.4.0 against a 0.3.x server gets
`404` from `/auth/cli/start` and prints
`This server does not support browser login; use anchor login --with-password`.
