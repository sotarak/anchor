# Anchor 0.4.0: MCP server for AI agents, authorized with OAuth

Status: proposed (2026-11-07). Ships in release **0.4.0**. Builds on typed values and the sensitive
flag (`2026-11-07-v0.4.0-typed-values-design.md`) and reuses the browser-approval pattern of
`2026-11-07-v0.4.0-cli-browser-login-design.md`.

## Intent

Developers work with AI coding agents (Claude Code, Codex, Cursor, ...). They want the agent to see
which secrets a project has, add or change them, and only read a sensitive value when the person
explicitly allowed it. The agent connects to Anchor as a remote MCP server and the person approves
it in the dashboard with OAuth, the way they approve `anchor login`.

## Decisions (with the user)

- **Capabilities:** the agent can read structure and metadata, read **non-sensitive** values, and
  create/update/delete secrets. Reading a **sensitive** value needs a separate permission,
  `secrets:reveal`, that the person ticks on the consent page (off by default). Every reveal is
  audited.
- **OAuth:** Anchor is its own OAuth 2.1 authorization server, stored in D1 (no KV, no third-party
  provider). Revocation takes effect on the next request.

## Threat model notes

- Anything an MCP tool returns enters the model's context and may be logged by the AI provider.
  Hence sensitive values only with `secrets:reveal`, and no reference expansion unless revealing
  (a non-sensitive `${DB_PASSWORD}` must not leak the password).
- A token acts as the approving user, limited by its scopes. Project roles still apply: a viewer's
  agent cannot write even with `secrets:write`.
- The MCP endpoint accepts only OAuth access tokens as `Authorization: Bearer`. Session cookies,
  CLI sessions and service tokens are refused there; OAuth tokens are refused on `/api/*`.
- Anonymous endpoints (register, token) are capped per IP and globally, like `cli_logins`.

## Scopes

| Scope | Grants |
|---|---|
| `secrets:read` | list projects, environments, folders, secrets (metadata), non-sensitive values, history |
| `secrets:write` | set and delete secrets |
| `secrets:reveal` | sensitive values in `get_secret` with `reveal: true` |

A client that asks for no scope gets `secrets:read secrets:write`. `secrets:reveal` is granted only
if the client requested it **and** the person ticked it.

## OAuth endpoints (all on the instance origin)

- `GET /.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp`
  (RFC 9728): `{ resource: "<origin>/mcp", authorization_servers: ["<origin>"], scopes_supported,
  bearer_methods_supported: ["header"] }`.
- `GET /.well-known/oauth-authorization-server` (RFC 8414): issuer `<origin>`, endpoints below,
  `response_types_supported: ["code"]`, `grant_types_supported: ["authorization_code",
  "refresh_token"]`, `code_challenge_methods_supported: ["S256"]`,
  `token_endpoint_auth_methods_supported: ["none"]`, `scopes_supported`.
- `POST /oauth/register` (RFC 7591 dynamic client registration): public clients only
  (`token_endpoint_auth_method: "none"`). 1-10 `redirect_uris`, each `https:`, or `http:` on
  `localhost`, `127.0.0.1` or `[::1]`; no fragments. `client_name` up to 100 characters (default
  `MCP client`). Returns 201 with `client_id`.
- `GET /oauth/authorize`: a dashboard page (SPA). Signed out → `/login?redirect=...`. It validates
  the request through the API, then shows the client name, the redirect host, the scopes in plain
  words, a **"Also allow reading sensitive values"** checkbox (only when `secrets:reveal` was
  requested; unchecked), and Approve / Deny. Copy:
  `Only approve if you just connected an AI agent or app to Anchor.`
- `POST /oauth/token`: `application/x-www-form-urlencoded`.
  - `authorization_code`: `code`, `redirect_uri`, `client_id`, `code_verifier` (PKCE S256,
    required). Codes live 5 minutes and are single-use; a reused code revokes its grant.
  - `refresh_token`: `refresh_token`, `client_id`. Refresh tokens rotate; presenting a used one
    revokes the grant.
  - Access tokens `anc_oat_...` live 1 hour; refresh tokens `anc_ort_...` 30 days from issue.
    Response `{ access_token, token_type: "Bearer", expires_in: 3600, refresh_token, scope }`,
    `Cache-Control: no-store`. Errors are RFC 6749 JSON `{ error, error_description }`.
- `POST /oauth/revoke` (RFC 7009): revokes the token's grant; always 200.
- A `resource` parameter, when sent (RFC 8707), must equal `<origin>/mcp`.
- Redirect URI matching is exact, except that a loopback redirect may use any port (RFC 8252).
- An invalid `client_id` or `redirect_uri` is shown on the page and never redirected to; other
  errors redirect with `error=` and `state`.

Only sha256 hashes of codes and tokens are stored. Disabled users get `invalid_grant` and their
access tokens stop working.

The metadata, register, token and revoke endpoints and `/mcp` answer CORS with
`Access-Control-Allow-Origin: *` (no credentials), so browser-based MCP clients work; none of them
reads cookies. These paths run in the Worker before static assets (`run_worker_first`), while
`/oauth/authorize` stays a dashboard page.

## MCP endpoint

`/mcp`, MCP Streamable HTTP, stateless (no session id), JSON responses; `GET` returns 405. Without
a valid token: 401 with `WWW-Authenticate: Bearer
resource_metadata="<origin>/.well-known/oauth-protected-resource/mcp"` (plus
`error="invalid_token"` when a token was presented). Server name `anchor`, version = release version.

Tools (all take slugs; `path` defaults to `/`):

| Tool | Scope | Result |
|---|---|---|
| `list_projects` | read | slug, name, the person's role |
| `list_environments` | read | slug, name |
| `list_folders` | read | subfolder paths |
| `list_secrets` (`include_imports?`) | read | key, path, type, sensitive, version, comment, updatedAt, `value` only for non-sensitive, importedFrom |
| `get_secret` (`reveal?`) | read (+reveal) | metadata; value if non-sensitive; a sensitive value only with `reveal: true` and `secrets:reveal` (expanded, audited as `secret.read`) |
| `secret_history` | read | versions without values |
| `set_secret` (`value`, `type?`, `sensitive?`, `comment?`) | write | created/updated/unchanged + metadata |
| `delete_secret` | write | deleted |

Read-only tools carry `readOnlyHint`; `delete_secret` carries `destructiveHint`. A missing scope is
a tool error naming it: `This needs the secrets:reveal permission. Remove and reconnect the Anchor
MCP server, and tick "Also allow reading sensitive values".` (write: `... secrets:write ...`).
Errors never contain values.

Audit: existing events gain `via: "mcp"` and `clientId` in metadata when made through MCP; new
actions `oauth.authorized`, `oauth.denied`, `oauth.revoked`.

- Account → **Connected apps**: client name, scopes, approved, last used, **Revoke**.

## Limits

- Pending (never-authorized) clients: 10 per IP and 500 overall; purged after 24 hours by the daily
  cron, with expired codes and tokens.
- Each `/oauth/token` and `/oauth/register` call is anonymous; the WAF rule from
  `operations/rate-limiting.md` covers `/oauth/*`.

## Non-goals

Client ID Metadata Documents, confidential clients, MCP prompts/resources, SSE streams, stateful
sessions, per-project scoping of a grant, consent for service tokens.

## Approaches considered

1. **Own authorization server on D1 (chosen).** Immediate revocation, no new binding, same storage
   and audit as the rest of Anchor. Costs more code.
2. **`@cloudflare/workers-oauth-provider`.** Less code, but adds a KV namespace to every deploy,
   revocation through eventually consistent KV, and a library API in flux.
