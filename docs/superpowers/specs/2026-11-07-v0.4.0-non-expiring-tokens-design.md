# Anchor 0.4.0: service tokens without an expiry

Status: proposed (2026-11-07). Ships in release **0.4.0**.

## Intent

Long-lived machines (a home server, an internal deploy box) use a service token and today it must
be rotated at most every 365 days, which breaks deploys when someone forgets. The owner wants the
option of a token that stays valid until it is revoked.

## Decisions

- A service token may be created with **no expiry**. It stays valid until revoked.
- Default stays 90 days everywhere; "no expiry" is an explicit choice.
- Who can create one: whoever can create service tokens today (project admins). No extra role.
- Revocation is unchanged and immediate (D1).

## Behavior

**API.** `POST /projects/:project/service-tokens` body field `expiresInDays` becomes
`number (1-365) | null`; `null` means no expiry. The field stays required, so a 0.3.x client (which
always sends a number) is unaffected and an omitted field is still a 400. `ServiceTokenDto.expiresAt`
becomes `number | null`. The `service_token.created` audit metadata records `expiresAt: null`.

**Storage.** Migration `0007_service_token_no_expiry.sql` rebuilds `service_tokens` with
`expires_at INTEGER` (nullable), copying every row. Authentication accepts a token when
`revoked_at IS NULL AND (expires_at IS NULL OR expires_at > now)`.

**CLI.** `anchor tokens create --expires-in <days|never>`; `never` sends `null`. The success line
says `never expires` instead of a date, and `tokens list` shows `never` in the EXPIRES column and
`active` in STATUS. With `never`, the CLI prints on stderr:
`warning: This token stays valid until you revoke it`.

**Dashboard.** The "Expires in" select gains **No expiry** (last option). Choosing it shows the
hint `The token stays valid until you revoke it.` The tokens table shows `Never` in Expires; the
status is `Active` (never `Expiring`/`Expired`).

**Docs.** `guides/ci.md` (service tokens), `guides/cli.md` (flag), `guides/dashboard.md`,
`reference/http-api.md`, `security/model.md` (a token without expiry is a standing credential:
scope it narrowly, prefer `read`, revoke when unused).

## Non-goals

Expiry reminders, token rotation helpers, changing the expiry of an existing token.

## Approaches considered

1. **Nullable column (chosen).** Honest data, simple checks, one table rebuild.
2. **Sentinel date (year 9999).** No migration, but every reader must special-case the sentinel
   and the DTO would still claim a date.
