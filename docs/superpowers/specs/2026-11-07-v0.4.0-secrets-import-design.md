# Anchor 0.4.0: `anchor secrets import`

Status: proposed (2026-11-07). Ships in release **0.4.0** and builds on typed values
(`2026-11-07-v0.4.0-typed-values-design.md`).

## Intent

Moving an existing service onto Anchor means entering dozens of keys. zepo-engine alone has
`application.config.yaml` (nested, about 100 leaves) and four `apps/<service>/.env` files, and
today each key needs its own `anchor secrets set`. `anchor secrets import` loads a whole file into
one environment and folder, with types inferred, so a service can switch to `anchor run` the same
day.

## Decisions (with the user)

- **Formats:** dotenv, JSON and YAML. Nested JSON/YAML objects are flattened into UPPER_SNAKE keys.
- **Existing keys:** skipped and reported by default; `--overwrite` writes a new version for them.
- **Sensitivity:** every key is sensitive unless it matches a repeatable `--non-sensitive <glob>`.

## Command

```
anchor secrets import (--from-file <path> | stdin) [--format dotenv|json|yaml]
                      [--overwrite] [--non-sensitive <glob>]... [--comment <text>] [--dry-run]
```

- Target is the usual `--project`, `--env` and `--path` (or `.anchor.json`).
- The format comes from `--format`, otherwise from the extension: `.json` is json, `.yaml` and
  `.yml` are yaml, and `.env` or a name starting with `.env` is dotenv. Stdin, or any other name,
  needs `--format`.
- CLI only in 0.4.0, with no new server endpoint: it uses `GET` (list, no reveal) and `PUT`.

## Mapping a file to secrets

**dotenv:** parsed with the bundled `dotenv` parser. Every value is `type: "string"`, since the
format has no types and no guessing is done.

**JSON/YAML:** the document must be an object (otherwise exit 2: `The file must contain an object
at the top level`). Walk it depth-first:

| Node | Result |
|---|---|
| object | recurse; the key path grows by one segment; an empty object is skipped as empty |
| string | `pem` if `checkTypedValue("pem", s)` passes, otherwise `string` |
| number | `number`, value `String(n)` |
| boolean | `boolean`, value `"true"` or `"false"` |
| array of strings only (or empty) | `list`, value `JSON.stringify(arr)` |
| any other array | `json`, value `JSON.stringify(arr)` |
| `null` (for example `api_key:` with nothing after it) | skipped and reported as **empty**; no secret is created |

**Key names:** each segment has `-`, `.` and spaces replaced with `_`, and is uppercased; segments
are joined with `_`. So `configs.openrouter.api_key` becomes `CONFIGS_OPENROUTER_API_KEY` and
`transporters.grpc-clients` becomes `TRANSPORTERS_GRPC_CLIENTS`. Before any write, the whole file is
rejected (exit 2, nothing written) when:

- a resulting key fails `secretKeySchema`: `Cannot import <source path>: <KEY> is not a valid key`;
- two source paths give the same key: `<path A> and <path B> both become <KEY>`;
- a value fails its type check or exceeds 64 KiB: `<KEY>: <reason>`. The value is never printed.

## Writing

1. Parse and validate everything (above). Any error stops before the network.
2. List the target folder (local secrets only, `reveal=false`) to learn which keys exist.
3. Plan each entry: `create`; `update` (it exists and `--overwrite` is set); `skip` (it exists,
   no `--overwrite`); `empty` (null or empty object).
4. `--dry-run` prints the plan and stops.
5. Otherwise send `PUT {value, path, type, sensitive, comment?}` for each `create`/`update`, one at
   a time and in key order. Stop at the first failure with exit 1 and
   `Imported <n> of <m>; <KEY> failed: <error>. Re-run to continue`. A re-run is safe: done keys are
   skipped, or are unchanged no-ops under `--overwrite`.

- `--non-sensitive <glob>` matches the final key, is case-sensitive, supports `*` and `?`, and is
  repeatable. Everything else is sensitive.
- With `--overwrite`, the imported type and flag replace the existing ones (the dry-run shows it).

## Output (never values)

The table (stdout) has KEY, TYPE, SENSITIVE (`yes`/`no`) and ACTION columns, then a summary line:
`Created <a>, updated <b>, skipped <c> existing, <d> empty in <env>:<path>`. With `--json`:
`{ created: string[], updated: string[], unchanged: string[], skipped: string[], empty: string[] }`
(`unchanged` = an `--overwrite` PUT that made no new version). A dry-run with `--json` adds
`dryRun: true` and puts the planned keys in the same arrays.

## zepo-engine walkthrough (documented in `guides/cli.md`)

```sh
anchor secrets import --from-file application.config.yaml --env prod --path /shared \
  --non-sensitive 'CONFIGS_CONTEXT_*' --non-sensitive 'CONFIGS_AGENT_*' --dry-run
anchor secrets import --from-file apps/service-agent/.env --env prod --path /service-agent
```

Then replace each value in `application.config.yaml` with its placeholder
(`api_key: ${CONFIGS_OPENROUTER_API_KEY}`) and start the service with `anchor run`.

## Non-goals

- Importing in the dashboard; generating the templated YAML; a server-side batch endpoint
  (all-or-nothing); syncing deletions.

## Approaches considered

1. **CLI-side parse + sequential PUTs (chosen).** No server change, idempotent re-runs, and each
   write audited as usual. The cost: an interrupted import is partial until it is re-run.
2. **Server batch endpoint.** Atomic, but it is a new write path with its own authorization, size
   limits and audit shape, all for a one-time migration step.
