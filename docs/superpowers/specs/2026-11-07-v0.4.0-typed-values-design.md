# Anchor 0.4.0: typed values and the sensitive flag

Status: proposed (2026-11-07). Ships as release **0.4.0** (server, dashboard and CLI share one
version).

## Intent

Anchor stores every secret as an untyped string. That works for env vars, but not for a real
service config such as zepo-engine's `application.config.yaml`: about 80% of it is non-secret
tuning (`timeout_ms`, `use_ssl`, `provider_order`, ...), and the secret part includes structured
values (`JWT_ACCESS_SIGNING_KEYS` is JSON, `jwt.access_keys` holds PEM public keys). 0.4.0 lets a
value declare what it is, so Anchor can reject malformed values on write, show non-secret config
in the clear, and export typed JSON/YAML. The goal is to move zepo-engine's config into Anchor
without workarounds.

## Goals

- Every secret version has a **type**: `string` (default, today's behavior), `json`, `pem`,
  `number`, `boolean`, `list`.
- Every secret version has a **sensitive** flag (default `true`). Non-sensitive values are returned
  without `reveal` and shown unmasked in the dashboard.
- The value is validated against its type on every write (API, CLI, dashboard).
- `anchor export --format json|yaml` writes typed values; `dotenv` and `anchor run` keep the
  canonical string.
- Old clients (CLI 0.3.x) keep working against a 0.4.0 server.

## Non-goals (0.4.0)

- Generated secrets, URL masking, `enum`, `duration` (candidates for 0.5.0).
- Server-side templating or rendering of config files.
- JSON Schema validation of `json` values.

## Anti-goals

- A type or sensitive flag that a database writer can change without detection. Flipping
  `sensitive` to `false` would expose a value without `reveal` and without a `secret.read`
  audit event.
- Breaking existing ciphertext, KEK rotation, or values written by 0.3.x.

## Decisions

### Storage (decided with the user: type is per version)

- Migration `0005_typed_values.sql` adds three columns to `secret_versions`:
  - `value_type TEXT NOT NULL DEFAULT 'string'`, CHECK in the six types
  - `sensitive INTEGER NOT NULL DEFAULT 1`, CHECK in (0, 1)
  - `aad_format INTEGER NOT NULL DEFAULT 1`, CHECK in (1, 2)
- The value is still one AES-256-GCM ciphertext of the canonical string. The type and flag are
  plaintext metadata, so the server can validate and list without decrypting. Accepted leak: a
  database reader learns which secrets are PEM, JSON, and so on, but not their values.
- Rollback restores the old version's value, type and flag together (it writes a new version
  through `putSecret`, as today).

### Integrity: AAD v2

- New versions are sealed with
  `anchor/secret/v2|<projectId>|<environmentId>|<secretId>|<version>|<type>|<0|1>` and stored with
  `aad_format = 2`.
- Rows with `aad_format = 1` (everything written before 0.4.0) keep the v1 AAD and are **always
  read as `string` + sensitive**, whatever their `value_type`/`sensitive` columns say. This makes
  tampering with a v1 row's columns harmless.
- Tampering with a v2 row's `value_type` or `sensitive` makes the decrypt fail
  (`IntegrityError` → 500), the same as a swapped ciphertext.
- KEK rotation re-seals each row with the AAD of that row's own format and leaves `aad_format`
  unchanged.

### Canonical string forms and validation

The stored value is the exact text the user sent. Validation only accepts or rejects it, and never
rewrites it.

| Type | Accepted text | Decoded (typed export) |
|---|---|---|
| `string` | anything (existing 64 KiB limit) | the string |
| `json` | `JSON.parse` succeeds (any JSON value) | the parsed value |
| `pem` | one or more PEM blocks: `-----BEGIN <LABEL>-----` and a matching `-----END <LABEL>-----`, body lines in base64 (RFC 7468 `Name: value` header lines allowed), `\n` or `\r\n` line endings, surrounding whitespace allowed | the string |
| `number` | JSON number grammar `^-?(0\|[1-9]\d*)(\.\d+)?([eE][+-]?\d+)?$` and finite | `Number(text)` |
| `boolean` | exactly `true` or `false` | the boolean |
| `list` | a JSON array whose elements are all strings | the array |

Rejection reasons (exact copy; never include the value):

- json: `not valid JSON`
- pem: `not a PEM block`
- number: `not a number`
- boolean: `must be true or false`
- list: `must be a JSON array of strings`

Server error: `400 bad_request`, message `value is not valid for type <type>: <reason>`.

### Write semantics

- `PUT .../secrets/:key` takes optional `type` and `sensitive`. When omitted on an existing secret,
  the current version's values are kept, so CLI 0.3.x can update a `json` secret and the value is
  still validated as JSON. When omitted on a new secret, the defaults are `string` / `true`.
- A put whose value, comment, type and flag all equal the current version is a no-op (no new
  version), as today.
- Audit `secret.created` / `secret.updated` metadata gains `type` and `sensitive`.

### Read semantics (decided with the user: show non-sensitive values without reveal)

- `SecretDto` and `SecretVersionDto` gain `type` and `sensitive`.
- A list without `reveal` includes `value` for non-sensitive secrets: the **stored** value, never
  expanded. It records no `secret.read` audit event, because the value is config, not a secret.
  A list with `reveal=true` behaves as today, including the audit event.
- References (`${...}`) expand only in `string` values. Other types are always literal, so a typed
  value cannot change shape after validation. A `string` value may still reference a typed
  secret and gets that secret's stored text.
- Authorization is unchanged: non-sensitive values are still encrypted at rest and readable only
  by principals with `secret:read` on that environment and path.

### CLI

- `anchor secrets set KEY [--type <type>] [--sensitive | --no-sensitive]`. Both flags are optional
  and are inherited from the current version when omitted. The value is checked locally before it
  is sent; the error is `Value of <KEY> is not valid for type <type>: <reason>` (exit 2, usage).
- `secrets list` gains a TYPE column. It shows a VALUE column when `--reveal` is given, or when any
  row is non-sensitive; sensitive rows show `********` without `--reveal`.
- `secrets get` without `--reveal` prints the value of a non-sensitive secret instead of the mask.
- `export --format json|yaml` writes decoded typed values; `dotenv` writes the canonical string.
  `run` injects the canonical string (unchanged).

### Dashboard

- The add/edit sheet gets a Type select and a "Sensitive" checkbox (default checked), and
  validates the value with the same shared checker before submitting.
- The secrets table shows a type tag next to the key for non-`string` types, and shows
  non-sensitive values in the clear (no reveal button).

## Approaches considered

1. **Per-version columns + AAD v2 (chosen).** Rollback is exact, tampering is detected, and old
   rows need no migration. Costs an AAD format switch and a rotation change.
2. **Per-secret columns on `secrets`.** Simpler schema, but rollback can pair an old value with a
   new type, and the columns cannot be bound into the version AAD without re-sealing on every type
   change. Rejected with the user.
3. **Type encoded inside the ciphertext (an envelope `{type, value}`).** Integrity for free, but
   listing types or non-sensitive values needs a decrypt for every row, and every reader of
   ciphertext changes. Rejected: costs more than option 1 for the same guarantees.
