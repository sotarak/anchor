# Anchor 0.5.0 (design)

Status: proposed. Follows the 0.4.0 release (2026-11-08).

## Intent

The owner asked for the next release to carry:

- the fixes and hardening that the 0.4.0 final review deferred;
- the lessons of the 0.4.0 release run;
- two features: **conditional reads (ETag / 304)** and **`anchor run --watch`**.

The owner chose features A + C from the proposal (push over webhooks/SSE is deferred), and chose
0.5.0 over 0.4.1 because the release adds features.

Two facts from the code motivate the features:

- `GET /secrets?reveal=true` writes one `secret.read` audit row per request.
- The SDK refreshes a folder once per `ttlMs` (60 s by default), so every service instance
  writes about 1,440 audit rows a day, even when nothing has changed.

A 304 carries no values, so it is not a read and needs no audit row. That removes almost all of
this noise, and makes polling cheap enough for `run --watch`.

## Goals

1. Conditional reads on the secrets list:
   - The server sends an `ETag` on every list and answers `304` to a matching `If-None-Match`,
     without an audit row.
   - The SDK and the CLI send `If-None-Match` when they hold a previous answer.
2. `anchor run --watch`: restart the child when its secrets change, without a long-lived
   connection.
3. Fix the deferred findings that affect users:
   - OAuth: re-approval leaves older grants live.
   - OAuth: the consent page alters `state`.
   - OAuth: the registration cap is counted per IPv6 address instead of per /64.
   - SDK: nested values are mutable.
   - SDK: races with a slow store.
   - SDK: an abort inside `onEvent` is missed.
   - SDK: a folder opened from a warm cache refreshes too late.
4. Make the release pipeline survive a package published outside CI, or a registry that is slow
   to show a new version.
5. Correct the docs. Tighten the weak tests.

## Non-goals

- Push notifications: webhooks, SSE, WebSockets or Durable Objects.
- ETags on any endpoint other than the secrets list.
- Caching responses in browsers or CDNs: API responses stay `Cache-Control: no-store`.
- Restarting on changes to files other than secrets (nodemon territory).

## Anti-goals

- A 304 served for a body that differs from the one the client holds.
- An ETag that lets anyone holding it test guesses of a secret value offline.
- A restart storm: restarting when values did not change, or several children alive at once.
- A watch mode that kills the child, or stops forwarding signals, when Anchor is unreachable.

## Approaches

### Conditional reads

1. **A keyed hash of the response body (chosen).** It is correct by construction: whatever
   changes the body changes the tag, including references, imports, permissions, types and
   comments. It still pays the decrypt cost, but it removes the audit row, the transfer and the
   client-side decode.
2. **A hash over version metadata only, without decrypting.** It is cheaper, but expanded
   references and imports change values without changing any version of the folder's own
   secrets. One missed dimension leaves clients stuck on stale values forever.
3. **Hono's `etag()` middleware.** It hashes the plaintext body with an unkeyed SHA-1, and runs
   after the handler has already written the audit row.

### Watch

1. **Poll with `If-None-Match` (chosen).** No new infrastructure. Polls are nearly free once
   304s exist.
2. **Push.** Deferred together with feature B.

## Behavior

### Server: `GET /api/v1/projects/:p/environments/:e/secrets`

- The order of work is unchanged: authorization, compose, then the response.
- The tag is computed from the exact JSON body about to be sent:
  `ETag: "<base64url of the first 16 bytes of HMAC-SHA-256(etagKey, body)>"`.
  It is a strong tag.
- `etagKey` is derived from `ANCHOR_ROOT_KEY` with HKDF-SHA-256 (empty salt, info
  `anchor/etag/v1`). It is a non-extractable HMAC key, imported once per isolate, and the raw
  bytes are zeroed after import.
  - Rotating the root key changes every tag. The only cost is one full response per client.
  - The previous root key is never used for tags.
- `If-None-Match` follows RFC 9110 weak comparison: a comma-separated list, `W/` prefixes
  ignored, and `*` matches any current representation. On a match:
  - the server answers `304` with no body, the `ETag` header and `Cache-Control: no-store`;
  - no audit row is written, with or without `reveal`.
- Otherwise the server answers 200 with the `ETag` header. It writes the `secret.read` audit
  row first, as today, and fails closed.

### SDK

- `CacheEntry` gains `etag?: string`. Entries written by 0.4.0 have none and simply send no
  `If-None-Match`.
- A fetch with a cached entry that has an `etag` sends `If-None-Match`, even with
  `fresh: true`, because a 304 is an answer from the server.
  - On 304, the new entry is `{ secrets: <the same array>, fetchedAt: now, etag }` and is
    written to the store.
  - With `cache: false`, the SDK sends no conditional requests.
- A folder that receives an entry with the same `secrets` array keeps its decoded values, so a
  304 never re-decodes.
- The `retry` / `refresh_failed` / `store_failed` events are unchanged; there is no new event.
- Budget: `dist/index.js` stays under **20 KB**. This raises the 0.4.0 budget of 16 KB; the
  bundle is 16,178 bytes today. This is the author's call, and the owner may override it.

### SDK fixes

- **Deep freeze.** Values a folder hands out (`get`, `toObject`) are frozen recursively.
  `loadSecrets` still returns fresh, mutable objects on every call.
- **Abort inside `onEvent`.** A retry wait rejects with `aborted` at once when the signal is
  already aborted, for example by `onEvent` itself.
- **Initial staleness.** A folder counts staleness from the opened entry's `fetchedAt`, not from
  the time it was opened. A folder opened from a warm shared store therefore refreshes at most
  `ttlMs` after that entry was fetched.
- **Ordering.** A folder never replaces its snapshot with an entry whose `fetchedAt` is older
  than the current one.
- **Slow stores.**
  - `SecretCache` joins an in-flight fetch for the key before reading the store.
  - It also remembers the newest entry it fetched for each key, in memory per instance, and
    serves the newer of that entry and the store's.
  - So a slow `get` that returns an entry older than a fetch that just finished never starts a
    second fetch.

### `anchor run --watch`

- Flags:
  - `--watch`: off by default.
  - `--watch-interval <seconds>`: an integer, default 30, minimum 5. Anything else exits 2 with
    a usage error.
  - `--watch-interval` without `--watch` exits 2.
- The first fetch is fail-closed, as today: no child starts without values.
- While the child runs, every interval does a conditional fetch:
  - **304, or a 200 whose child environment equals the current one:** the child keeps running
    (with a 200, the tag is updated).
  - **A different environment:** stderr shows `Secrets changed; restarting <cmd>`, without keys
    or values. The child gets SIGTERM; if it has not exited after 10 s, it gets SIGKILL. Then
    the child starts again with the new environment. Only one child is ever alive.
  - **A failed poll** (network, 5xx, 401/403): the child keeps running with its current values.
    The first failure after a success prints `Could not check Anchor for changes (<message>);
    keeping the current values` on stderr. Recovery prints `Reconnected to Anchor`. The next
    interval tries again.
- When the child exits on its own (not because of a restart), `anchor` stops watching and exits
  with the child's code. SIGINT, SIGTERM and SIGHUP are forwarded as they are today, so stopping
  `anchor` stops the child and the loop.
- On Windows, SIGTERM ends the child at once. This is documented.

### OAuth fixes

- **Re-approval.** Approving a client revokes the person's earlier active grants for the same
  client, in the same request that creates the new grant. `oauth.authorized` metadata gains
  `revokedGrants: <n>` when n > 0.
- **Consent `state`.** The consent page reads OAuth parameters from the raw query string, never
  through the router's JSON parsing. `state` values such as `true`, `null`, `1e3`,
  `12345678901234567890` and `"quoted"` round-trip byte for byte.
- **Registration cap per /64.** The pending-registration cap counts IPv6 addresses by their /64
  prefix. IPv4 addresses, including IPv4-mapped IPv6 (`::ffff:a.b.c.d`), count as the full
  address. The normalized key is what `oauth_clients.ip` stores from now on.

### Release pipeline

- npm publishes go through `scripts/npm-publish.mjs`.
  - When `npm publish` fails, the script checks `npm view <pkg>@<version>` every 30 s, up to 10
    times. If the version is visible, it reports a notice and succeeds; otherwise it fails with
    npm's error.
  - The skip-checks stay in place.
- `scripts/dual-declarations.mjs` recurses into subdirectories and keeps their relative layout.
- Actions: `actions/checkout@v7` and `actions/upload-pages-artifact@v5`, as in Dependabot PRs
  #9 and #10.

### Docs

- **SDK guide:**
  - refresh is triggered by reads (there is no timer), and the SDK sends conditional requests;
  - with `cache: false` there are no conditional requests;
  - a 304 is not audited.
- **CLI guide:** `run --watch`.
- **HTTP API reference:** `ETag` / `If-None-Match` on the secrets list.
- **Audit retention guide:** reads that answer 304 write no audit row.
- **CHANGELOG:** CLI 0.3.x shows a service token without expiry as expired in 1970; upgrade the
  CLI.

### Tests to tighten

- The MCP test where a viewer is denied asserts the exact message.
- The NestJS module is tested against an unreachable Anchor (a network error, not a 403).
