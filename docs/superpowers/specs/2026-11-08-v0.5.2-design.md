# Anchor 0.5.2: folder imports from the CLI (design)

## Intent

Folder imports (one folder shows the secrets of another, e.g. `shared:/` into `prod:/api`) exist on
the server, the HTTP API and the dashboard since M5, but the CLI can only *read* through them. A
developer or an agent setting up a project from the terminal has to stop and ask someone to click
**Add import** in the dashboard; the `anchor-migrate` skill says exactly that today. 0.5.2 lets the
CLI list, add and remove imports, and updates the skills and docs so an agent can finish a migration
without the dashboard.

Behavior the person asked to confirm (no change, documented): imports are resolved on every read,
not copied. A key added to the source shows up in the importing folder on the next read; local keys
win, earlier imports win, only the source folder itself (no subfolders, not transitive). A running
`anchor run` needs a restart or `--watch`; an exported file is a snapshot.

## Goals

- `anchor imports list | add | remove` for the folder chosen by `--env` / `--path` (defaults from
  `.anchor.json`, like every other command).
- Skills `anchor-cli` and `anchor-migrate` use the commands instead of sending the person to the
  dashboard; docs (`guides/cli.md`, `guides/references-imports.md`) describe them, including the
  live-link behavior above.
- Release 0.5.2 (CHANGELOG, versions, the usual pins).

## Non-goals

- No server, API or schema change: the CLI uses `GET/POST /imports` and `DELETE /imports/:id` as
  they are.
- No reordering of imports (the API has none); no SDK or MCP write tools for imports.
- `anchor secrets import` (file import) is unchanged.

## Anti-goals

- Confusing the two "import" commands: help text and docs must say which is which.
- Printing secret values: these commands handle folder addresses only.

## Approaches

- **A. Top-level `anchor imports list|add|remove` (chosen by the person).** Matches the API name
  `/imports` and the CLI's `noun verb` shape; the risk is the name next to `secrets import`, handled
  by help text.
- B. `anchor folders imports list|add|remove`: ties imports to folders but adds a third level no
  other command has.
- Renaming `secrets import`: breaks scripts, rejected.

## Design

**Source address.** `<env>:<path>`, the same form references use (`${prod:/db/PASSWORD}` →
`prod:/db`). `shared:/` and `shared:/db` are valid; `shared` alone means `shared:/` (my call: the
root is the common case). The path is normalized with `normalizeSecretPath`; a bad address is a
usage error (exit 2) with an example.

**`anchor imports list`** — the imports of `--env:--path`, in the order they apply (position).
Human output: one line per import, `1  shared:/` style, plus "No imports in <env>:<path>" when
empty (stderr info, like `folders list`). `--json`: `FolderImportDto[]` as the API returns it.

**`anchor imports add <source>`** — appends an import. Idempotent: if the folder already imports
that source, success with `created: false` ("Already imports shared:/ into prod:/api"), the way
`folders create` treats an existing folder (the API's 409 for a duplicate becomes this no-op).
`--json`: `{ import, created }`. Errors pass through: importing itself (400, exit 2), unknown
environment (404, exit 5), no write access to the folder or no read access to the source (403,
exit 4).

**`anchor imports remove <source>`** — removes the import of `<source>` from the folder, found by
listing the folder's imports (the person never handles ids). Confirms like other destructive
commands ("Stop importing shared:/ into prod:/api?"; non-TTY needs `--yes`), because the folder's
apps lose those keys on their next read. No such import: exit 5 with the folder's current imports
in the hint. `--json`: `{ removed: FolderImportDto }`.

**Help text.** The `imports` group says "Make a folder show the secrets of another folder (not to be
confused with `secrets import`, which loads a file)"; `secrets import` gets the mirror sentence.
Each subcommand has examples; the help snapshot is updated.

**Skills.** `anchor-migrate` step 2: add the shared-folder import with
`anchor imports add shared:/ --env <env> --path <folder>` (dry-run-free: it is idempotent and
reversible) and verify with `anchor imports list`. `anchor-cli`: a quick-reference row and the
three commands in `references/commands.md`. Skill edits follow the writing-skills discipline
(a baseline scenario before the change).

**Docs.** `guides/cli.md`: command table rows, a short "Imports" section, `--json` shapes in the
output contract table. `guides/references-imports.md`: CLI as a third way to manage imports, and a
"When changes show up" list with the live-link behavior.

## Left to the builder

- Where the address parser lives (next to `folderArg` in `commands/folders.ts` or a new
  `commands/imports.ts`), and the exact human output columns.
- Whether `add` lists first or reacts to the 409; both must end at `created: false`.
