# Anchor 0.6.0: two-factor authentication and passkeys (design)

## Intent

Accounts are email and password only. The security model lists "No SSO or MFA yet" as a gap, and
accepts that an attacker with many addresses can keep guessing one account's password. 0.6.0 adds
an opt-in second factor (TOTP or a passkey, with recovery codes) to password login, so a leaked or
guessed password alone no longer signs anyone in. Passkeys also defeat phishing of the login page.

Because CLI browser login and MCP/OAuth consent both require a dashboard (`web`) session
(`requireWebUser`), protecting dashboard login protects them too. The one other door, CLI
password login (`anchor login --with-password`), gets the same second step.

## Decisions (chosen by the owner, 2026-11-22)

1. **Scope:** TOTP + recovery codes + passkeys as a **second factor**. No passwordless login yet.
2. **Policy:** opt-in per user. No instance-wide enforcement yet.
3. **Password reset keeps MFA.** A reset link sets a password only. Clearing someone's MFA is a
   separate **Reset 2FA** action: owners for anyone but themselves, admins for members only
   (the password-reset rule), audited, and it revokes the target's sessions and OAuth grants.
4. **Step-up** for every MFA change: enabling or disabling TOTP, adding or removing a passkey,
   regenerating recovery codes. The dashboard session must have re-authenticated in the last
   10 minutes.
5. **Dependencies:** `@simplewebauthn/server` (server) and `@simplewebauthn/browser` (web) for
   WebAuthn; `uqr` (web) for the TOTP QR code; TOTP itself (RFC 6238) written on WebCrypto
   HMAC-SHA-1.

## Threat model

Server-side model, unchanged. The server must read the TOTP secret to check codes, so it is
sealed with the **root key** (AES-256-GCM, AAD `anchor/totp/v1|<userId>`). A D1 dump alone does
not reveal it; root-key rotation re-wraps it with the project KEKs. Passkey public keys are not
secret; recovery-code hashes are salted per user and slow, so a dump cannot be swept for every user
at once.

| Attacker | 0.5.3 | 0.6.0 with MFA enabled |
|----------|-------|------------------------|
| Knows or guesses the password (leak, reuse, distributed guessing) | Signs in | Stopped at the second step; factor guesses are capped per account |
| Cracks a PBKDF2 hash from a D1 dump | Signs in | Stopped at the second step (the TOTP secret is sealed by the root key) |
| Phishes password + TOTP code on a fake page | Signs in | Still signs in with TOTP; **stopped by a passkey** (bound to the origin) |
| Holds a stolen session cookie | Acts as the user | Same, and cannot change MFA without re-authenticating |
| Holds a password-reset link | Takes the account | Sets the password, still needs the factor |
| Talks the user into approving a CLI code | Gets a CLI session | Same (out of scope) |

Accepted residual risks, documented: an attacker who knows the password can lock the account's
second step for 15 minutes (5 wrong codes); passkeys are bound to the hostname they were created
on (a second hostname or a domain change makes them unusable there; recovery codes still work).

## Behavior

### Login

1. `POST /auth/login` checks limits and the password as today. If the user has MFA (a confirmed
   TOTP or at least one passkey), it answers `200 { mfaRequired: true, ticket, methods, expiresAt }`
   and creates no session. `ticket` is `anc_mfa_<base64url 32 bytes>`, stored as SHA-256, lives
   5 minutes, remembers `client`. `methods` lists `totp` (if confirmed), `passkey` (if a passkey
   exists for this request's hostname) and `recovery` (always). Users without MFA get today's
   response.
2. `POST /auth/login/mfa { ticket, method: "totp" | "recovery", code }` or the passkey pair
   `POST /auth/login/passkey/options { ticket }` → `POST /auth/login/passkey { ticket, response }`
   finishes the login, creates the session for the ticket's `client` (cookie for `web`, token for
   `cli`) and consumes the ticket.
3. Limits: 5 failures per ticket (then the ticket is deleted); 5 factor failures per account in
   15 minutes (`login_attempts` key `m|<userId>`), counted at login and at step-up; success
   deletes the account key. A ticket stops working when the user is disabled, their MFA is reset,
   or their password is changed or reset.
4. Audit: `auth.login` with `method` `password+totp`, `password+passkey` or `password+recovery`
   (plus `recoveryCodesRemaining` for recovery); failures are `auth.login_failed` with reason
   `mfa_invalid` or `mfa_locked`.

### TOTP

SHA-1, 6 digits, 30-second period, accepts the previous, current and next step, 20-byte secret
shown as RFC 4648 base32 (upper case, no padding). Each accepted step is recorded and a code for
the same or an earlier step is refused (no replay), atomically. Enrollment: setup returns the
secret and an `otpauth://` URI (issuer `Anchor (<hostname>)`); a correct code confirms it.

### Recovery codes

10 codes `xxxxx-xxxxx` over `abcdefghijklmnopqrstuvwxyz234567`, stored as PBKDF2-SHA-256
(10,000 iterations, salt `anchor/recovery/v1|<userId>`) of the normalized code (lower case, no `-`
or whitespace), each usable once. (Amended in the final review: 50 bits are too few for an
unsalted fast hash, which a D1 dump could sweep for every user at once.) Generated and shown once
when the account goes from no MFA to MFA; regenerated on demand (old ones stop working); deleted
when the last factor is removed.

### Passkeys

WebAuthn second factor. RP ID = the request's hostname, expected origin = the request's origin,
RP name `Anchor`, attestation `none`, resident key `preferred`, user verification `preferred`.
Challenges live 5 minutes and work once. Each credential stores its RP ID, COSE public key,
counter, transports, backed-up flag and a name (1–64 chars, at most 20 per user). A counter that
goes backwards fails verification.

### Step-up (re-authentication)

Every dashboard session records `reauth_at` (set at creation). MFA management endpoints need a
`web` session sent as the cookie with `reauth_at` within 10 minutes, or answer
`403 reauth_required`. `POST /auth/reauth` refreshes it: with the password when the user has no
MFA; with a TOTP code, a recovery code or a passkey when they do.

### Admin

The Users list shows whether each user has MFA (`mfaEnabled`). **Reset 2FA**
(`POST /users/:id/mfa-reset`) deletes the target's TOTP, passkeys, recovery codes and pending
tickets, clears their `m|` lock, revokes their sessions and OAuth grants, and audits `mfa.reset`.
Break-glass documents the SQL for an instance whose only owner lost every factor.

## Non-goals

Passwordless/usernameless passkey login, instance-wide MFA enforcement, SMS or email codes,
step-up for actions other than MFA changes, SSO.

## Compatibility

- Additive migration `0010_mfa.sql`. Users without MFA see no change.
- `/auth/login` gains a second response shape. A 0.5.x CLI doing password login against an
  account with MFA fails with "The server did not return a CLI session"; browser login works.
- Root-key rewrap also re-wraps TOTP secrets; the response gains `totpRewrapped`.
